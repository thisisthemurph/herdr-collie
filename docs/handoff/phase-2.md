# Phase 2 hand-off: controller core

Branch `phase-2`, based on `main` at `43df444` (Phase 1 and CI).

## What was built

`packages/controller`, one module per job:

| Module | Job |
| --- | --- |
| `src/main.ts` | `collie-controller [--home <dir>]`: takes the lock, recovers, ticks every 50 ms; SIGTERM or SIGINT flush and release the lock |
| `src/lock.ts` | `controller.lock`, created with `O_EXCL`. A live holder makes a second controller exit 1 with a message naming it; a dead pid's lock (or garbage) is replaced and logged. |
| `src/home.ts` | The `~/.collie` layout, atomic JSON writes (temp file, fsync, rename), durable appends |
| `src/machines.ts` | The run, ticket and execution state machines as transition tables |
| `src/reducer.ts` | Pure `reduce(state, event)` and `rebuild(runId, events)`: `state.json` from `events.jsonl` |
| `src/runlog.ts` | One run: events are appended with one `write()`, then reduced. `state.json` is written at most every 250 ms and on flush. Loading rebuilds from the log, cuts a torn tail and logs when `state.json` was behind. |
| `src/inbox.ts` | The inbox watcher: offsets, incomplete lines, de-duplication, envelope checks, the controller's `done` verification, and the effects of `ask`, `done` and `fail` |
| `src/commands.ts` | The `ctl` command handlers |
| `src/controller.ts` | Orchestration: recovery, the control channel, leases, run completion, legal-transition checks |

**`collie ctl`** (in `packages/cli/src/ctl.ts`):
- It is called as `collie ctl <command> '<args JSON>'`, or with `--args-file`, and takes `--json`.
- It validates locally, naming the field, then writes `control/pending/<id>.json` atomically and waits for the reply.
- It exits at once with 6 when there's no live lock, and with 6 after 10 seconds when the lock's process never answers.

**Commands:**
- **Supported:**
  - board commands: `board.create`, `board.update_settings`, `ticket.set_preparation`, `ticket.pull_in`, `dep.override` / `dep.restore`;
  - config: `profile.save`, `workflow.save`;
  - run commands: `run.start` (snapshot, leases, carry-over), `run.pause` / `run.resume` / `run.cancel`, `run.delete`;
  - other run actions: `ticket.cancel`, `exec.cancel`, `question.answer` (recorded; delivery is Phase 4).
- **Return `unsupported`, naming the phase:** `board.import` and `board.refresh` (Phase 3), `ticket.investigate` and `ticket.retry` (4), `pr.mark_ready` (6).

**Contract changes**, all additive (schema, fixtures and `docs/protocol.md` updated):
- **Inbox verdict events:**
  - `agent.event_accepted` and `agent.event_rejected` gain `offset`, so inbox offsets can be rebuilt from the log;
  - `agent.event_rejected` may have `caused_by: null`, for a line with no readable id.
- **New events:** `ticket.attention_added` and `ticket.attention_removed`, which close the Phase 0 gap: round cap, failed execution and delivery error now have events.
- **State:** `state.json` executions gain optional `agent_blocked`.
- **New file shapes:** `controller.lock` and `leases.json` (`validateLock`, `validateLeases`).
- **Ticket state machine:** two entry transitions, `— → pending` at `run.start` and `— → completed` for carried-over tickets.
- **Log contents:** only accepted agent events are copied into `events.jsonl`.
- **Typing fix:** the schema's timestamp validators are now typed `Schema<string>`. Before, every timestamp field's inferred type was `unknown`.

**Fixtures:**
- `fixtures/runs/complete/state.json` is now generated by the reducer from the complete run. That closes another Phase 0 gap.
- `fixtures/scenarios/controller-inbox.jsonl` and its `.expected.jsonl` are new.

`make build` now also compiles `dist/collie-controller`.

## Deviations from the docs, and why

1. **Executions are seeded in tests.** Phase 2 has no scheduler or launcher, but the inbox
   watcher needs executions. Tests write the events Phase 4's launcher will write
   (`seedExecution` in `test/helpers.ts`), then a real controller recovers them. The
   controller has no ctl command for creating executions, on purpose.
2. **Rejected lines aren't copied into `events.jsonl`.** Retention says inbox content is
   "already in `events.jsonl`". That is true for accepted lines only. A rejected line
   stays in its inbox, named by its rejection. Copying it would let the reducer apply,
   say, a finding sent after `done`. I changed the Phase 0 complete-run fixture to match.
3. **`controller.log`** is new in the layout. It holds recovery notes, stale-lock
   replacements and internal errors, never secrets.
4. **Refused `ctl` commands exit 2.** The protocol's exit codes cover only arguments
   (2) and "not running" (6). A refused command's code and message are printed, and
   `--json` prints the controller's reply.

## Every `DECISION:`

| Where | Decision |
| --- | --- |
| `machines.ts` | A ticket enters a run as `pending` (readiness is computed from Phase 3 on), or as `completed` when carried over |
| `runlog.ts` | A torn final line of `events.jsonl` is cut off on recovery |
| `inbox.ts` | Only accepted agent events are copied into `events.jsonl` |
| `inbox.ts` | An agent reporting while its execution is `starting` moves it to `working` (hc may lag the agent). Reports from a `created` execution are rejected. |
| `inbox.ts` | The controller's `done` verification in Phase 2: a reviewer's verdict must match its blocking findings, and a developer's `done` must list commits. Checking those commits against the branch needs the worktree, so it arrives in Phase 4. |
| `inbox.ts` | What a finished execution means for its ticket (review, remediation, delivery) is the workflow's job, from Phase 4 on. Phase 2 records the result, withdraws its questions, and resumes a ticket whose attention empties. |
| `reducer.ts` | Questions are withdrawn by the execution's final state change, with no event of their own |
| `commands.ts` | Board defaults come from the protocol's example board |
| `commands.ts` | A board's id is its `board.create` command's id, and a run's id its `run.start` command's id, so re-applying after a crash is a no-op |
| `commands.ts` | `board.create` needs `jira.cloud_id` until Phase 3 looks it up |
| `commands.ts` | `question.answer` records the answer (`delivered: false`); delivery is Phase 4 |
| `home.ts` | `controller.log` |
| `ctl.ts` | On a 10-second timeout, the command is left in `pending/`, because a slow controller may still apply it |
| `ctl.ts` | A refused command exits 2 |
| `events.ts` (schema) | `agent.event_rejected` may have `caused_by: null` |

## Known gaps

- **PID reuse.** A lock is stale only when its pid is dead. After a reboot another process
  could hold that pid, and the controller would refuse to start until the lock file is
  deleted. The fix is to record and compare the process start time; Phase 7 hardening.
- **`control/done/`** keeps every reply, and the controller logs nothing about board
  commands, since a board has no event log. Retention of `done/` belongs in Phase 7.
- **Leftover `*.tmp` files** from a `kill -9` during an atomic write stay behind. They are
  harmless and ignored, but not cleaned up.
- **Polling, not file watching.** The loop ticks every 50 ms. It's simple and reliable;
  `fs.watch` could cut idle CPU later.
- **`dep.override`** edits the board only. Its effect on readiness, including in a running
  run, is Phase 3.

## Suggestions (out of scope)

- Phase 3 should compute readiness as a pure function over the run snapshot plus overrides,
  and emit `pending → blocked/ready` from it.
- Phase 4's launcher should create the execution folder and `execution.json` before
  emitting `execution.created`. The test helper does the folder part today.

## Demo

```sh
make build && make check                        # dist/collie, dist/collie-controller; 331 tests
export COLLIE_HOME=$(mktemp -d)
dist/collie-controller &                        # takes controller.lock
dist/collie-controller; echo "exit $?"          # 1: another controller is running
for p in developer security-reviewer; do dist/collie ctl profile.save --args-file fixtures/files/profile/valid/$p.json; done
dist/collie ctl workflow.save --args-file fixtures/files/workflow/valid/standard-feature.json
B=$(dist/collie ctl board.create --json '{"name":"Payments","jira":{"site":"[SITE].atlassian.net","project":"PAY","cloud_id":"[CLOUD-ID]"},"repo":{"workspace":"[WORKSPACE]","slug":"[REPO]","default_branch":"main","local_path":"~/code/[REPO]"}}' | jq -r .result.board_id)
# Boards get tickets from Jira in Phase 3; add one by hand for now:
jq '.tickets = {"PAY-1": {"summary":"One","jira_status":"To Do","status_category":"new","resolution":null,"blocked_by":[],"on_board":true,"preparation":"ready","workflow":null,"fetched_at":"2026-11-09T10:00:00Z"}}' \
  $COLLIE_HOME/boards/$B/board.json > $COLLIE_HOME/b.json && mv $COLLIE_HOME/b.json $COLLIE_HOME/boards/$B/board.json
R=$(dist/collie ctl run.start --json "{\"board_id\":\"$B\"}" | jq -r .result.run_id)
dist/collie ctl run.pause "{\"run_id\":\"$R\",\"reason\":\"lunch\"}"
dist/collie ctl ticket.retry "{\"run_id\":\"$R\",\"ticket\":\"PAY-1\"}"; echo "exit $?"   # 2: unsupported, Phase 4
kill -9 $(jq -r .pid $COLLIE_HOME/controller.lock)
dist/collie ctl run.resume "{\"run_id\":\"$R\"}"; echo "exit $?"     # 6: not running
dist/collie-controller & sleep 1                # replaces the stale lock, recovers the paused run
dist/collie ctl run.resume "{\"run_id\":\"$R\"}"
dist/collie ctl run.cancel "{\"run_id\":\"$R\"}"
jq -c '{type, payload}' $COLLIE_HOME/runs/$R/events.jsonl
cat $COLLIE_HOME/controller.log
kill $(jq -r .pid $COLLIE_HOME/controller.lock)
```
